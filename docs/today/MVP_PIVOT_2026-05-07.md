## 1. Princípio

A GiroB2B é um **reverse marketplace B2B**: a vitrine não exibe produtos de vendedores; exibe **necessidades de compradores**. O comprador publica o que precisa; vendedores assinantes contatam o comprador via WhatsApp.

Hipótese a validar: **vendedores B2B pagam assinatura mensal pelo direito de receber leads qualificados**. O lead = uma necessidade publicada e visível. A monetização é parte do MVP — não fica para depois.

Esta inversão é deliberada. O modelo clássico (vendedor publica produto, comprador busca) está saturado e tem barreira de entrada de catálogo. Tirando o catálogo do caminho, conseguimos: (a) onboarding de comprador grátis e em segundos; (b) volume de leads imediato; (c) clareza do que cada lado paga.

## 2. O que está na vitrine

| Antes (modelo clássico) | Agora (reverse marketplace) |
|---|---|
| Card de **produto** (nome, foto, preço) | Card de **necessidade** (título, qtd, prazo, cidade) |
| Página `/produto/[slug]` SSR | Página `/necessidade/[slug]` SSR |
| Comprador clica "Solicitar cotação" → modal complexo | Vendedor clica "Contatar via WhatsApp" → wa.me com mensagem pronta |
| Catálogo de fornecedores | Lista de necessidades publicadas |
| Inquiry direta + chat interno + pipeline | Sem chat, sem pipeline. WhatsApp é o canal único. |

UX visual: marketplace estilo Mercado Livre/Amazon (densidade de informação no card, filtros laterais, busca com autocomplete) — adaptado ao tema visual GiroB2B (teal + dourado, BRIEF_MARCA 2026-04-17).

## 3. Papéis

### 3.1 Comprador (buyer)
- Cadastro **grátis**, mínimo: email + senha + nome.
- **Sem CNPJ obrigatório.** Sem onboarding multi-step.
- Pode publicar quantas necessidades quiser.
- Recebe contato de vendedores via WhatsApp (com consentimento explícito).

### 3.2 Vendedor (supplier)
- Cadastro com CNPJ obrigatório (BrasilAPI quando reativada).
- **Paga assinatura mensal** para ver detalhes da necessidade e clicar em "Contatar".
- Vê listagem completa em modo preview (título, categoria, cidade), mas botão de contato exige conta + assinatura ativa.
- Pode operar em ambos os papéis (dual-role) — uma conta paga só pelo lado supplier.

### 3.3 Admin
- Inalterado em conceito. Vê todas as necessidades, modera, suspende usuários.
- Painel já separado em `admin.girob2b.com.br`.

### 5.3 Schema novo (migration `036_demands.sql`)

Tabela `demands` (renomeia/expande `search_needs`):

```sql
demands (
  id uuid pk,
  buyer_user_id uuid fk -> auth.users,
  slug text unique,                       -- /necessidade/[slug]
  title text not null,
  description text not null,
  category_id uuid fk -> categories,
  subcategory_slug text,
  quantity numeric,
  unit text,
  budget_max_cents bigint,                -- opcional
  deadline date,
  delivery_city text,
  delivery_state char(2),
  whatsapp_number text not null,          -- consentimento explícito do buyer
  photos_urls jsonb,                      -- até 3 fotos opcionais
  status text check (status in ('open','negotiating','fulfilled','cancelled')),
  views_count int default 0,
  contact_count int default 0,
  published_at timestamptz default now(),
  expires_at timestamptz default now() + interval '30 days',
  created_at timestamptz default now(),
  updated_at timestamptz default now()
)
```

Decisão sobre `search_needs`: ficar como tabela legada congelada (2 registros existentes), copiar manualmente o que houver de aproveitável para `demands` durante o desenvolvimento.

Coluna `subscription_status` em `suppliers` (ou tabela `supplier_subscriptions`): para o paywall. MVP usa enum simples `('inactive','trial','active','expired')` — Stripe/MP entra na fase 2.

Padrão idêntico ao implementado no checkbox LGPD do antigo formulário de inquiry (commit `8d9d243`, RF-01.08). Texto:

## 7. Decisões já tomadas (não reabrir sem motivo)

1. **Visual:** mantém tema GiroB2B (teal + dourado). Inspiração de layout: marketplaces majors (Mercado Livre, Amazon, OLX) — pesquisa de referência será feita antes da Fase 4/5.
2. **Não-assinante vê tudo em preview:** título, categoria, cidade, descrição, prazo. **Apenas o botão "Contatar via WhatsApp" é gated.** Estilo LinkedIn Premium — tensão saudável, sem hostilidade.
3. **Clique em "Contatar" sem conta:** abre modal "Criar conta + Ver planos" que reusa os planos da landing page. Modal tem botão **"Continuar explorando"** que fecha sem ação. Captura intenção sem forçar.
4. **`expires_at` da necessidade:** 30 dias com auto-arquivamento. Buyer pode renovar. Sumir cedo = mau sinal de mercado. Sumir tarde = poluição de feed.
5. **WhatsApp gate:** `wa.me/<numero>?text=<mensagem-pre-formatada>`. Mensagem inclui: nome do vendedor, título da necessidade, link da página da necessidade. Sem API WhatsApp Business — link direto.
6. **Tabela `search_needs`:** congelada. Nova tabela `demands`.
7. **Tabelas de chat/pipeline/proposal/inquiry:** congeladas no banco, sem drop. Drop só pós-validação de zero uso por 60 dias.

## 8. Decisões abertas (a tomar antes de Fase 5)

- **Preço da assinatura do vendedor.** Tem que estar definido até a Fase 5 (paywall + landing).
- **Ferramenta de cobrança:** Stripe ou Mercado Pago. Recomendação técnica: Mercado Pago (PIX nativo no público B2B BR).
- **Como o admin "ativa" um vendedor pra teste antes da cobrança automatizada:** botão manual em `/admin/usuarios`? Flag em `supplier_subscriptions`? Definir no início da Fase 5.
- **Filtro de WhatsApp por estado/cidade do supplier:** vendedor de SP recebe lead de RJ? Default: **sim, vê tudo**, com filtro opcional. Validar com Gustavo se quer comportamento mais restrito.

## 9. Riscos conhecidos

- **WhatsApp scraping:** se número fica visível no HTML em preview, bots colhem. Mitigação: número só aparece após `is_subscribed = true` E click em "Contatar" (registra em `contact_log` para auditoria).
- **Spam de demandas:** buyer pode poluir o feed. Mitigação: rate limit por buyer (3 demandas/dia), moderação reativa pelo admin, status `cancelled` por admin.
- **LGPD:** consentimento explícito no formulário de publicação cobre o compartilhamento; a política de privacidade já lista vendedores como categoria de compartilhamento.
- **Migração de mentalidade do CEO:** O relatório `_RELATORIO_VITOR_2026-05-06.md` foi escrito 1 dia antes deste pivô. Os 17 docs técnicos historicos vão ficar **temporariamente inconsistentes** até serem revisados em Fase 10. Aceitamos esse débito documental como custo do pivô.
